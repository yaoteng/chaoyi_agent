# 潮驿直播 开源化战略方案（条件不足时的替代路径）

> **触发**：当前不具备申请 ICP 证 / 网文证等牌照的条件，探讨"改为开源项目以获得社区支持"的可行性。
> **版本**：v1.0 ｜ **日期**：2026-09-03 ｜ **性质**：战略备选方案（PM + 法务共审）
> **配套**：《潮驿直播PRD.md》《潮驿直播合规检查清单.md》《潮驿直播牌照资质路线图.md》（同目录）

---

## 0. 核心结论（先答问题）

- **开源"代码"不需要任何牌照**；但**运营"面向公众的中国直播服务"仍需牌照**。二者是不同层面：开源解决"研发 + 社区 + 产品验证"，不解决"经营资质"。
- **可行路径**：把潮驿直播从"待运营的产品"重构为"**开源、可自建的直播社交平台套件**"，以开发者 / 垂类小社群为目标用户，先在 GitHub/Gitee 攒 star 与贡献者；公开运营 + 牌照推迟到有主体/资本时，或转向**海外/自建部署**。
- **你们已有验证过的打法**：FMCG 分销 SaaS 正在冲 GitHub 1000+ stars（零依赖 Node.js 后端、架构文 + 掘金软文）。潮驿直播可直接复用这套"开源攒社区"方法论。

---

## 1. 牌照 vs 开源：边界澄清（法务视角）

| 行为 | 是否需要中国牌照 | 说明 |
|---|---|---|
| 发布源码到 GitHub / Gitee | **否** | 软件分发，非经营性互联网信息服务 |
| 用户自行部署（自建 self-host） | 否（对部署者自负） | 部署者自行承担其运营地合规 |
| 你方运营公开服务（中国，含打赏） | **是** | ICP 证(B25) + 网文证(网络表演) + … |
| 你方运营公开服务（海外） | 按属地 | 遵守当地法律（如 GDPR、当地电信/文化规） |
| 代码内置打赏但不运营 | 否（代码层面） | 一旦你方运营即触发牌照 |

> **红线**：不能以"开源"为名，实际运营一个无牌的公开直播服务（尤其含打赏）。提供可自托管软件（如 Owncast / LiveKit / SRS）本身是合法且普遍的——包括国内的 ossrs/srs。

## 2. 四种可行模式

| 模式 | 描述 | 牌照压力 | 适合度 |
|---|---|---|---|
| **A. 开源引擎/框架** | 类 SRS/LiveKit/Owncast，开发者自托管；潮驿=可自建的直播社交套件 | 最低（你方不运营） | ⭐⭐⭐ 推荐现阶段 |
| **B. 开源 + 海外运营** | 代码开源，公开实例部署在非中国区域，遵守当地法 | 按属地 | ⭐⭐ 若接受海外用户 |
| **C. 社区版(开源) + 云托管版(未来持证)** | 双轨：开源攒社区，未来持证后开官方托管 | 运营版需牌照 | ⭐⭐⭐ 长期最优 |
| **D. 先开源攒社区，条件具备再申请牌照公开运营** | bootstrap：用社区/星标/贡献验证需求，再补主体与资本 | 推迟到运营时 | ⭐⭐⭐ 务实路径 |

**推荐**：现阶段以 **A 落地**，长期走向 **C/D 结合**。

## 3. 定位重构：从"产品"到"平台套件"

- **Slogan 候选**：「Own your live community · 自建你的潮流驿站」
- **目标用户**：开发者、垂类社群（校园电台 / 潮玩圈 / 美食圈 / 手作圈）、小型公会、企业内训。
- **差异化卖点**（正好是你已有的资产）：
  - 合规内置：年龄门禁、打赏限额 hooks、内容审核接口预留——作为**负责任的开源特性**对外宣传。
  - 四端打通（Web / KMP / 鸿蒙 / 小程序）。
  - WebRTC 推拉流 + FLV/HLS 兜底，可自托管（SRS 一键起）。
- **不做**：你方不运营公开含打赏的服务（避免牌照触发）。

---

## 4. 开源策略（复用你的 star 打法）

- **License**：MIT 或 Apache-2.0（商用友好，吸引企业用户与贡献者）。
- **双托管**：GitHub（主，冲 star）+ Gitee（国内镜像，覆盖中国开发者；GitHub 在国内访问不稳）。
- **README 四件套**：定位 → 快速启动（`docker-compose up`）→ 架构图 → 合规说明（开源≠无合规，自托管责任声明）。
- **沿用 FMCG SaaS 经验**：架构技术文 + 掘金软文（外部 GitHub 链接）、示例 demo、清晰 CONTRIBUTING。
- **社区**：Issue 模板、Discord / 微信群、贡献者指南、Good First Issue 标签。

---

## 5. 已有资产盘点（可直接开源）

| 资产 | 开源亮点 | 注意 |
|---|---|---|
| SRS + WebRTC 推拉流 | 实时媒体底座，自托管友好 | 已在用 ossrs/srs |
| 四端（Web/KMP/鸿蒙/小程序） | 全端覆盖 | 小程序需剥离 AppID 等私密配置 |
| 合规 hooks（年龄/限额/审核接口） | 负责任的差异化卖点 | 保留为 feature，勿删 |
| `LiveStream` 模型（pullUrl/pushUrl/兜底） | 清晰接口 | 脱敏示例配置 |

> **脱敏要求**：开源前必须剥离/脱敏密钥、真实域名、用户数据、内部配置；提供 `.env.example` 而非 `.env`。

---

## 6. 仍不可逾越的红线（即使开源）

1. 你方**不能以开源为名**实际运营无牌公开直播服务（尤其含打赏）。
2. 代码**不得内置**绕过未成年保护 / 内容审核的能力。
3. 合规 hooks 保留为**卖点（feature）**，不是负担——这恰是潮驿区别于野路子的地方。

## 7. 开源阶段路线图

| 阶段 | 动作 | 产出 |
|---|---|---|
| **O1** | 代码整理 + License + `.env.example` 脱敏 + `docker-compose` 一键起 | 可自托管仓库 |

## 8. 与现有 PRD / 合规清单的关系

- **PRD 转为"开源版 PRD"**：MVP 仍是直播 + 弹幕 + 礼物(合规版) + 兴趣匹配 + 语音房，但定位改写为"可自托管平台套件"，目标用户改为开发者/社群。
- **合规清单 L1–L6 转为"未来官方运营前置"**：开源阶段**不阻塞**开发；一旦你方要运营公开服务，再回到清单逐项过关。
- **牌照路线图依旧有效**：只是触发时点后移（运营时而非发布代码时）。

---

## 9. 风险

- star ≠ 营收；需设计开源可持续（GitHub Sponsors / 企业支持 / 未来云版）。
- 双许可 / 商业版的边界设计（避免社区版与商业版冲突）。
- 海外运营的属地合规成本。
- 社区对项目"是否真合规"的审视——务必把合规 hooks 做实，而非口号。
