# 示例：一个开源社区如何被「agent 化」

> 这是一个**示意性**改造记录（社区名 RustyCache 为虚构，流程真实可复现），用于展示潮驿 5 个 Skill 落到真实社群的样子。所有涉及对外发言的动作均为**草稿**，由维护者确认后执行（HITL）。

## 背景

**RustyCache**：一个 2.3k star 的 Rust 缓存库，2 名核心维护者（@alice、@bob），月均 60+ issue、15+ PR。痛点：

- 新人想贡献但「不知道从哪下手」，good first issue 常年为 0；
- issue 堆积、响应慢，重复问题反复出现；
- 发版靠手工翻 commit，release notes 经常漏人致谢；
- 文档只有中文，海外用户抱怨看不懂；
- 贡献者默默流失，没有表彰机制。

**月均运营工时估算：约 40 小时。**

## 改造步骤（用潮驿 5 个 Skill）

### ① community-onboarding —— 把「新人入口」立起来
对智能体说：
> 「分析我们仓库，设计贡献者入驻阶梯，标出适合 good first issue 的议题，并写两段欢迎话术。」

产出：
- 3 级入驻阶梯：文档/翻译（零门槛）→ good first issue（小代码）→ 进阶任务；
- 自动建议 8 个 `good first issue` 候选（附理由）；
- 两段欢迎话术（首次 PR / 首次 Issue）。

维护者确认后，打标 + 写进 `CONTRIBUTING.md`。**新人首周贡献数：0 → 5。**

### ② issue-triage —— 让「议题管家」每天上岗
对智能体说：
> 「把本周 open 的 issue 分类、定优先级、找重复项，并起草回复。」

产出：每行一条 `<链接> | 标签 | 优先级 | 重复于? | 回复状态`，并标出 3 个语义重复 issue、2 个安全相关 P0。

维护者点「确认」即批量打标/回复。**issue 平均首响：6 天 → 1 天。**

### ③ release-notes —— 发版不再手忙脚乱
对智能体说：
> 「基于 v0.3.0..HEAD 的 commit，生成发布说明和 CHANGELOG 段落。」

产出：按 `✨ 新功能 / 🐛 修复 / 📚 文档` 分组的 Release 文案 + `CHANGELOG.md` 的 PR-ready diff，自动 @ 本期贡献者。

维护者 review 后发 Release。**发版耗时：3h → 20min。**

### ④ doc-localization —— 把文档带上英文
对智能体说：
> 「把 docs/zh 同步出一份英文，标出待译段落并生成招募译者 Issue。」

产出：待译清单（文件 | 行号 | 篇幅）+ 译文草稿（代码块原样）+ 一个「招募译者」Issue 模板。

维护者把翻译任务作为 good first issue 派发。**英文文档上线，海外 issue 下降 30%。**

### ⑤ contributor-recognition —— 让贡献被看见
对智能体说：
> 「生成本月贡献者榜单与致谢文案，并指出幕后英雄（多 review 少 PR 的人）。」

产出：致谢文案 + 荣誉墙表格（按贡献类型分组）+ 「幕后英雄」特别名单。

维护者发到 Release 与社群频道。**当月核心贡献者流失：2 → 0。**

## 结果对比

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 月均运营工时 | ~40h | ~6h |
| 新人首周贡献 | 0 | 5 |
| issue 平均首响 | 6 天 | 1 天 |
| 英文文档 | 无 | 有 |
| 核心贡献者月流失 | 2 | 0 |

## 你该怎么复现

1. 把 `skills/` 下对应 Skill 复制到你的宿主 `skills/` 目录（见仓库 README 快速开始）；
2. 按上面的「对智能体说……」逐条触发；
3. 每个 Skill 的产出**先确认再执行**，把人工确认环节沉淀进你们自己的 `CONTRIBUTING.md`；
4. 把你们的改造记录 PR 到 `examples/`，成为下一个示例。

> 这就是潮驿想做的事：**让每一个小社群，都能拥有自己的数字社工。**
